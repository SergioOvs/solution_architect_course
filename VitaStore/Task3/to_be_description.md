# HLD для Vita Store
## Переход от «толстого» клиента к cloud‑native решению 
Вместо монолита POS App (Windows/C#) с жёстко встроенными драйверами оборудования вводится Web POS App. Это лёгкое 
приложение для планшета или браузера. Оно не содержит драйверов и бизнес‑логики — всё это вынесено в микросервисы 
облачного бэкенда (Cloud Backend). Благодаря этому магазин избавляется от локального сервера БД (MS SQL Express) и 
зависимости от Windows‑кассовых станций.

## Решение проблемы разнообразного местного «железа»
Для работы с разнородным оборудованием магазинов и автономности создаётся прослойка HAL Edge Device Bridge. Она 
устанавливается непосредственно в магазине и предоставляет унифицированный REST API для кассы. Внутри HAL реализованы 
отдельные адаптеры: Payment Terminal Adapter, Fiscal Printer Adapter. Эти адаптеры содержат специфические драйверы под 
разные модели терминалов и принтеров. Также выделены два критичных локальных компонента:
* Local Price Cache (SQLite): Локальное хранилище актуальных цен и остатков. Инициатором обновления всегда выступает
Web POS App. При старте смены или по кнопке «Обновить цены» в UI, posApp запрашивает у HAL инкрементальные обновления. 
HAL, в свою очередь, обращается к Pricing/Discount Service только если кэш пуст или устарел (TTL). При сканировании 
товара POS сначала обращается в этот кэш, что обеспечивает мгновенный отклик.
* Local Receipt Journal (SQLite/WAL): Локальный журнал чеков. HAL принимает чеки от кассы, сохраняет их в журнал 
в режиме Write-Ahead Logging (для защиты от внезапного отключения питания) и только после успешной записи отдает команду
на печать фискального чека. Для защиты от деградации накопителя установлен лимит журнала — 1000 чеков или 500 МБ. 
При достижении 90% заполнения диска HAL блокирует оплату картами и уведомляет администратора, разрешая только наличные.
Таким образом, Web POS общается только со стандартным интерфейсом HAL, а не напрямую 
с железом. При покупке нового магазина достаточно добавить новый адаптер в HAL, не меняя код кассовой программы.

## Обеспечение работы при обрыве связи (Offline‑mode strategy)
Магазин продолжает работать офлайн. HAL использует Local Price Cache для пробития товаров и Local Receipt Journal 
для накопления чеков. При печати чека HAL возвращает POS App локальный идентификатор транзакции.

## Синхронизация и защита от дублей (Online/Recovery)
Как только связь восстанавливается, HAL инициирует пакетную синхронизацию накопленных чеков по HTTPS в Cloud Backend.
* <b>Идемпотентность и защита от дублей:</b> Каждый чек в Local Receipt Journal имеет глобальный `receipt_uuid`, 
сформированный на стороне кассы. При отправке пакета HAL использует этот `receipt_uuid`. На стороне Cloud Backend 
создается таблица `processed_receipts` (или используется Redis Cluster). Перед обработкой транзакции бэкенд проверяет 
наличие `receipt_uuid`. Если ID уже есть, пакет пропускается, и бэкенд возвращает 200 OK с ID уже сохраненной 
транзакции. Это защищает систему от повторной отправки одного и того же чека при таймауте запроса на стороне HAL.
* <b>Подтверждение синхронизации:</b> После успешной записи чека в центральную БД Cloud Backend возвращает в HAL массив 
подтверждений `{ "receipt_uuid": "...", "status": "synced", "cloud_tx_id": "..." }`. HAL удаляет подтвержденные записи 
из Local Receipt Journal. Если подтверждение не получено (например, из-за падения сети после отправки), чек остается 
в журнале и будет повторно отправлен при следующем восстановлении связи.
* <b>Обработка ошибок:</b> Если штрихкод товара из чека не найден в SAP ERP, Cloud Backend помечает транзакцию флагом 
`requires_manual_review` и возвращает этот статус в HAL. Чек остается в журнале HAL со статусом
`error_manual_review_required`. Кассир не может удалить такой чек. В UI POS App доступна кнопка «Корректировать», 
которая позволяет найти товар по названию/артикулу, заменить штрихкод и повторно отправить исправленный чек под тем же 
`receipt_uuid`.

## Корректировка назначения Promo Engine
Promo Engine: Сервис расчета премий сотрудников. Отвечает за вычисление бонусов кассиров и руководителей на основе 
данных о продажах, среднего чека и выполнения KPI, передаваемых из Cloud Backend. Управление скидками и промо-акциями 
вынесено в отдельный сервис (Pricing/Discount Service), который обновляет Local Price Cache в HAL

## Сервис управления скидками (Pricing/Discount Service)
Управление скидками и промо-акциями вынесено в отдельный сервис — Pricing/Discount Service.
* <b>Триггеры акций:</b> Cloud Backend передает в Pricing/Discount Service данные о продажах. Для исключения
рассинхронизации Pricing/Discount Service слушает события из Kafka. При срабатывании условий акции 
(например, «выдай купон при покупке на сумму X») сервис принудительно обновляет Local Price Cache в HAL через фоновое 
событие или WebSocket/gRPC-вызов, не дожидаясь запроса от кассы.
* <b>Запрос цен:</b> Обновление кэша цен в HAL по инициативе кассира происходит по запросу со стороны HAL, который 
обращается к Pricing/Discount Service через REST API.

## Обработка возвратов (Refund)
Для обеспечения идемпотентности возвратов используется формат `receipt_uuid:refund:uuid` или передача
`original_receipt_uuid` в теле запроса. Таблица `processed_receipts` поддерживает хранение типа операции (`sale`, 
`refund`). При получении возврата Cloud Backend проверяет наличие исходного чека в SAP ERP и Event Store. Если исходная 
продажа не найдена, транзакция помечается флагом `requires_manual_review`.

## Безопасность Edge-узла
Для защиты персональных данных, содержащихся в чеках, Local Receipt Journal шифруется на диске (AES-256). 
Аутентификация HAL при подключении к Cloud Backend для синхронизации и запросов к Pricing/Discount Service 
осуществляется по протоколу mTLS. Ключи шифрования и сертификаты mTLS для аутентификации HAL при подключении 
к Cloud Backend выдаются и ротируются централизованной службой управления ключами (KMS). Ротация сертификатов происходит
автоматически каждые 90 дней.
