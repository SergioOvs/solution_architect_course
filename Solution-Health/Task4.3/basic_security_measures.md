#  Проектирование базовых мер безопасности
## Описание схемы аутентификации пользователей мобильного приложения
## Протокол
OAuth 2.0 Authorization Code Flow с PKCE (Proof Key for Code Exchange). Это индустриальный стандарт 
для нативных мобильных приложений. PKCE защищает от перехвата authorization code, а использование системного браузера 
изолирует процесс от самого приложения.

## Участники
* мобильное приложение (Native App)
* Authorization Server (AS) — Identity Provider (Keycloak, Auth0, Azure AD)
* External API Gateway — единая точка входа. Проверяет подпись JWT, применяет WAF и rate limiting по IP/installationId.
Не знает `sub`.
* Mobile API / BFF — внутренняя точка входа для мобильного трафика. Получает запрос от External Gateway 
(уже с валидным токеном). Извлекает sub из токена, выполняет object-level authorization и оркестрацию к Legacy-системам.

## Последовательность
1. Приложение генерирует `code_verifier` и `code_challenge`.
2. Перенаправляет пользователя в системный браузер на AS.
3. Пользователь аутентифицируется (логин/пароль, биометрия, SSO).
4. AS возвращает `authorization_code`.
5. Приложение обменивает `authorization_code` + `code_verifier` на `access_token` (JWT) и `refresh_token`.
6. `Access_token` используется для вызова API.

## Формат и способ передачи токена
* **Формат:** JWT (JSON Web Token) с подписью RS256 (асимметричная).
* **Способ передачи:** HTTP-заголовок `Authorization: Bearer <access_token>`.
* **Почему не в URL/cookies:** передача в URL логируется и подвержена утечкам; cookies для native-приложений
небезопасны без сложной настройки.

## Управление токенами
* **Access_token TTL:** 5–15 минут (короткий для снижения риска)
* **Refresh_token TTL:** 30–90 дней с ротацией
* **Хранение:** Secure Enclave (iOS) / Keystore (Android) с биометрической защитой
* **Revocation:** endpoint для отзыва токена при выходе или компрометации
* **App Attestation (SafetyNet / Play Integrity):** выдача `client_id` и `client_secret` производится только после 
успешной проверки подлинности устройства через Google Play Integrity API или Apple App Attest. Это предотвращает 
использование эмуляторов и поддельных версий приложения для получения токенов

## Защита от обнаруженных проблем
* **SQL-инъекция (INT-006):** устраняется на уровне **_Mobile API/BFF_** через параметризованные запросы и валидацию
по JSON Schema. **_External Gateway_** блокирует известные payload через WAF как дополнительный слой.
* **Подмена сессии (SD-007):** предотвращается тем, что **_Mobile API/BFF_** извлекает идентификатор пациента
исключительно из доверенного claim `sub` в токене, который проверил **_External Gateway_**. Параметры запроса (например,
`patientId` в URL или теле) игнорируются и не могут переопределить данные из токена. На каждом обращении к ресурсу 
(запись, результаты анализов) выполняется object-level authorization: `resource.owner_id == sub`.

## Обязательные меры защиты каналов передачи данных
1. Защита периметра (CDN/DDoS)
   1. Внешний рубеж: CDN (Cloudflare, CloudFront) с включённой DDoS-защитой перед API Gateway. Фильтрация вредоносного
   трафика до попадания в инфраструктуру
   2. WAF на уровне CDN/Gateway для блокировки известных атак (SQLi, XSS)
2. Транспортная безопасность (TLS)
   1. mTLS внутри контура: взаимная аутентификация между External Gateway и Mobile API/BFF, 
   а также между внутренними сервисами
   2. Управление сертификатами централизованное (Vault/cert-manager), автоматическая ротация, 
   короткоживущие сертификаты (TTL 24 часа)
   3. TLS 1.2 минимум, предпочтительно TLS 1.3
   4. Строгий набор шифров (AEAD), Forward Secrecy (ECDHE)
   5. HSTS (max-age=31536000; includeSubDomains; preload)
3. Аутентификация и авторизация
   1. OAuth 2.0 + PKCE
   2. JWT-проверка на API Gateway/BFF
   3. Управление сессиями: short TTL access_token, refresh_token rotation, device binding
   4. Zero Trust: каждый вызов к внутренним системам (1С, Расписание) требует отдельной авторизации
4. Защита API
   1. Rate limiting
   2. Idempotency-Key для всех mutating-запросов
   3. Input validation (JSON Schema), санитизация и output encoding
   4. Web Application Firewall (WAF) с OWASP CRS
   5. Версионирование схемы API и строгий CORS
   6. Circuit Breaker. Защита при вызове медленных Legacy-систем (1С, Расписание). При превышении тайм-аутов или доли
   ошибок — автоматическое размыкание цепи и возврат понятной ошибки клиенту, предотвращающая каскадный отказ
5. Защита данных
   1. Шифрование в покое (AES-256) для БД, кэшей, бэкапов
   2. Маскирование/токенизация персональных данных в логах
   3. Минимизация данных в JWT (не хранить медицинские данные в токене)
   4. Secrets management
6. Мониторинг и реагирование
   1. Мониторинг PKI: алерты на истечение сертификатов (за 7 дней), метрики latency mTLS handshake
   2. Мониторинг Rate Limiting: алерты на аномальный рост 429, дашборд X-RateLimit-Remaining
   3. SIEM: сбор событий аутентификации, 4xx/5xx, rate limit hits
   4. Алерты: множественные 401/429, необычные geo/IP, всплески ошибок
   5. Audit log: неизменяемый лог доступа к персональным данным (WORM-хранилище)
