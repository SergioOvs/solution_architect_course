# Описание к To-Be диаграмме
## Обзор механизмов защиты
В целевой архитектуре мы внедрили комплексные меры отказоустойчивости на всех уровнях системы:
* API Gateway как единый фасад обеспечивает аутентификацию (Auth Service), ограничение частоты запросов (rate limiting)
и централизованную обработку ошибок.
* Для критичных синхронных вызовов (платёжный шлюз, резервирование слота) настроены строгие тайм-ауты, 
retry с экспоненциальной задержкой и circuit breaker с состоянием half‑open. Это предотвращает каскадные сбои 
при недоступности внешних сервисов.
* Асинхронные потоки данных защищены механизмом Transactional Outbox, чтобы исключить потерю событий.
* Legacy-системы интегрированы через отдельные адаптеры (ACL-сервисы), что изолирует внутреннюю модель
от нестабильных контрактов.

## Механизмы защиты и отказоустойчивости
### Внешние взаимодействия через API Gateway
**API Gateway** выступает единой точкой входа для всех внешних клиентов (пациентов, врачей, администраторов). 
Это позволяет централизованно реализовать следующие механизмы:
* **Аутентификация и авторизация:** Все внешние запросы проходят проверку токена (_JWT_) с помощью выделенного сервиса 
аутентификации (_Auth Service_). Реализован принцип SSO (_Single Sign‑On_).
* **Rate limiting:** Ограничение частоты запросов на основе IP-адресов или идентификаторов пользователей предотвращает 
исчерпание ресурсов бэкенда при всплеске нагрузки или атаках.
* **Обработка ошибок:** Внутренние ошибки сервисов приводятся к единому формату ответа с полем `traceId`. 
Детали реализации не раскрываются клиенту, что повышает безопасность.

### Синхронные вызовы критичных сервисов
#### Платёжный шлюз
Операция списания средств — необратимый шаг процесса записи/оплаты. Для неё применён следующие защитные механизмы:
* **Тайм-аут:** жёстко ограничен (_1.2 секунды_), чтобы пользователь получал ответ в рамках допустимого ожидания.
* **Retry:** две попытки с экспоненциальной задержкой (_initialDelay = 200 мс_), чтобы сгладить кратковременные сбои 
платёжной инфраструктуры.
* **Circuit Breaker:** порог срабатывания `failureRate=50%`, время открытого состояния` 30 секунд`, 
состояние _half-open_ с тремя проверочными запросами. Это защищает систему от лавинного отказа при длительной
недоступности шлюза.
* **Transactional Outbox:** запись заказа в БД и публикация события об оплате происходят в одной транзакции. 
Это исключает риск потери событий из-за сетевых проблем между сервисом и Kafka.

#### Проверка полиса ДМС (через ACL-сервис => Legacy-система "Полисы")
Проверка фрода является компенсируемым шагом. Если она завершается неудачно или сервис временно недоступен, 
процесс записи может быть продолжен с пометкой о безопасности.
* **Тайм-аут:** короткий (`500 мс`), так как результат проверки не блокирует основной поток оформления заказа.
* **Fallback:** если сервис недоступен или отвечает слишком долго, заказ считается условно безопасным. 
Операцию повторения запроса (_retry_) здесь нет, так как это удлиняет ожидание пользователя без необходимости.

#### Резервирование слота врача (Inventory Service)
Это критичный синхронный вызов, необходимый для подтверждения записи.
* **Тайм-аут:**` 300 мс`.
* **Retry:** одна попытка с фиксированной задержкой (`100 мс`) для быстрого восстановления после временных сбоев.
* **Идемпотентность:** все операции резервирования снабжены ключом `Idempotency-Key`, чтобы исключить создание 
дублирующих записей при повторах.

### Асинхронная обработка через Event Broker (Kafka)
Все фоновые задачи (_уведомления, синхронизация CRM/LIS_) переведены на асинхронную модель Pub/Sub.
* **Гарантия доставки:** используется уровень `at-least-once` (`acks=all`, `retry on producer`).
* **Dead Letter Queue (DLQ):** сообщения, которые невозможно обработать стандартным потребителем, помещаются в DLQ
для последующего анализа и ручной коррекции.
* **Идемпотентность потребителей:** подписчики (_CRM, Уведомления_) проверяют уникальный идентификатор события 
перед обработкой, чтобы избежать дублирования действий.

### Anti‑Corruption Layer (ACL) для legacy-интеграций
Для интеграции с внешними системами (_LIS, 1С Полисы_) добавлены отдельные адаптеры (_ACL-сервисы_).
* Эти сервисы преобразуют данные из доменной модели "Здоровья+" к формату legacy-систем и обратно.
* Они изолируют сложность преобразования протоколов (_SOAP/XML => REST/JSON_) и нестабильность контрактов, 
обеспечивая слабую связанность новых микросервисов.

### Кластеризация и распределённые механизмы
* **Кластеризация API Gateway:** развёрнут за балансировщиком нагрузки минимум в трёх экземплярах. Общее хранилище 
для rate limiting обеспечивает согласованность квот.
* **Distributed Circuit Breaker:** состояние circuit breaker'а хранится в распределённом кешировании (_Redis/Hazelcast_). 
Это гарантирует, что решение о размыкании цепи принимается всеми репликами шлюза одновременно.
