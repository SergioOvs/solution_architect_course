# Architecture Canvas: RetailCore AS‑IS
## Value Proposition
Платформа оформления заказов с единым жизненным циклом заказа через разные каналы продаж _(Сайт, Мобильное приложение, 
Маркетплейсы)_.

Ключевая ответственность — устойчивый order flow при сохранении гибкости для коммерческих изменений _(промо-механики, 
новые партнёрские сценарии)_.

**Бизнес-кейс:**
* Повысить скорость вывода коммерческих фич без риска для конверсии checkout
* Подготовиться к отказу от зарубежных компонентов (Oracle) без остановки процессов

## Key Stakeholder
|      Роль       | Влияние/Интерес                                                                                                                                                                                                             |
|:---------------:|:----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Бизнес-спонсор  | Скорость вывода промо; прозрачность данных; поэтапная миграция (`CNST‑03`, `CNST‑09`); не приемлет big-bang миграцию. Приоритизирует устойчивость checkout (`CNST‑02`) и платформенную основу для новых сценариев (`FR‑16`) |
| Команда заказов | Устойчивость checkout (`CNST‑02`); устранение ручных обходных путей (`APP‑10`); единая модель статусов (`FR‑03`, `APP‑04`). Знает фактический жизненный цикл заказа                                                         |
|  Тех лид ядра   | Поэтапное выделение сервисов из монолита Java; снижение связности с базой данных Oracle (`APP‑05`, `APP‑07`). Предлагает выносить только наименее связанные сервисы                                                         |
|    Аналитика    | Единый источник правды для отчётов (`NFR‑10`, `GAP‑10`); снижение нагрузки на операционную базу напрямую (`APP‑08`). Страдает от расхождения цифр у маркетинга, финансов и операций                                         |

## Core Functions

|:----------------------------------:|:--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------:|
|         Checkout/Order API         | Оформление заказа; расчёт цены с региональными надбавками и сервисным сбором маркетплейсов. Историческое ветвление в коде                                                                   |   `FR‑01`, `FR‑17`   |
|      Промо-сервис + Fallback       | Расчёт скидок. Внешний микросервис опционален — при сбоях используется логика пакета Oracle                                                                                                 |       `FR‑06`        |
|          Delivery Routing          | Выбор маршрута доставки. Правила разбросаны по Java‑коду, таблицам Oracle и конфигурациям интеграционного слоя. Нет единого контракта                                                       |  `FR‑04`, `APP‑09`   |
|         Status Management          | Формально описан жизненный цикл статусов, но фактическое поведение зависит от технических состояний и реализовано в разных местах (batch-процессах, административных интерфейсах поддержки) |  `FR‑03`, `APP‑03`   |
|          Payment Gateway           | Синхронный вызов во время checkout. Узкое место под нагрузкой                                                                                                                               |  `FR‑05`, `APP‑06`   |
| Резервирование товаров/Cancelation | Логика частично живёт в пакетах базы данных                                                                                                                                                 |       `APP‑07`       |

**Важный вывод:** Наблюдаемость перестала быть технической деталью и превратилась в ключевую проблему уровня 
функциональности. Без единой прослеживаемой истории невозможно снизить стоимость поддержки и устранить споры о данных.

## Quality Requirements & Constraints
|   ID    | Содержание                                                            | Влияние                                                                                                                |
|:-------:|:----------------------------------------------------------------------|:-----------------------------------------------------------------------------------------------------------------------|
| CNST‑01 | Нельзя останавливать бизнес ради миграции. Только поэтапные изменения | Требует выделения безопасных швов (seams). Big‑bang неприемлем                                                         |
| CNST‑02 | Checkout, оплата и обещание доставки имеют высший приоритет риска     | Любое изменение здесь должно быть минимально-инвазивным                                                                |
| CNST‑03 | Каждый этап должен давать измеримую ценность                          | Без явного эффекта бизнес не примет изменения                                                                          |
| CNST‑04 | Большая инсталляционная база процессов и интеграций                   | Одномоментный переход невозможен.	Архитектура должна поддерживать параллельное существование старого и нового контуров |
| CNST‑05 | On‑premise инфраструктура, ресурсы близки к пределу                   | Медленное горизонтальное масштабирование. Требуется оптимизация запросов                                               |
| CNST‑06 | Централизованная БД Oracle ограничивает развитие                      | Исторические данные занимают десятки терабайт. Нужен вынос аналитики                                                   |
| CNST‑09 | Импортонезависимость важна, но не ценой остановки ключевых процессов  | Постепенная миграция, начиная с наименее рискованных зон                                                               |
| CNST‑10 | Критичные зоны меняются только поэтапно, с подготовкой отката         | Прямое рефакторинговое изменение недопустимо                                                                           |

## Business Context
* **Каналы продаж:** Сайт, Мобильное приложение, Маркетплейсы (_как канал_). Архитектурный риск: 
«одинаковый заказ = разный», так как логика зависит от канала, региона и правил.
* **Платежные провайдеры:** Синхронный вызов во время checkout. Высокий риск деградации.
* **Службы доставки/Склады:** Разрозненные способы интеграции (_REST, polling, staging tables_). Нет единого контракта.
* **Партнёрские площадки:** Отсутствие единой модели партнёрского контура.
* **Аналитика:** Нагружает оперативную базу напрямую (_direct SQL_). Отсутствует единый источник правды для отчётов.

## Components / Modules
* **Монолитное ядро (RetailCore A5‑15):** Java, Spring, монолитная архитектура. Ядро содержит историческую логику расчёта
цен, промо, резервирования товаров и управления статусами.
* **База данных ORACLE OLTB:** SPOF (точка отказа). Является хранилищем данных, движком бизнес-правил и точкой обмена 
данными с внешними системами (_Legacy DB Exchange Layer_). Содержит десятки ТБ исторических данных без архивации.
* **Промо-сервис:** Частично вынесен, частично реализован в пакете Oracle.
* **Интеграционный контур логистики:** Не существует единого слоя. Используются разные способы взаимодействия 
с партнёрами.

## Risks and Missing Information
### Risks
|   ID   |                        Риск                        | Описание                                                                                                                                       |
|:------:|:--------------------------------------------------:|:-----------------------------------------------------------------------------------------------------------------------------------------------|
| RSK‑01 |           SPOF (Single Point of Failure)           | Вся платформа держится на базе данных Oracle. Прямой доступ внешних систем (.NET Integration, аналитика) создаёт нагрузку на операционную базу |
| RSK‑02 |          Отсутствие единой модели статуса          | Клиент видит один статус, поддержка — другой, склад — третий. Это приводит к эскалациям и потере доверия клиентов                              |
| RSK‑03 | Наблюдаемость как проблема уровня функциональности | Поддержка работает как «ручной адаптер». Без единой прослеживаемой истории невозможно снизить стоимость поддержки и устранить споры о данных   |
| RSK‑04 |             Trade‑off скорости и риска             | Бизнес хочет быстрее выводить коммерческие фичи, но любое изменение в checkout сопряжено с высоким риском потери конверсии                     |
