# План трансформации RetailCore
## 1. Бизнес-цель
### Формулировка цели
Повысить скорость вывода коммерческих фич без риска для конверсии checkout и устойчивости критичных процессов. Создать 
безопасные границы вокруг ядра монолита, чтобы последующие изменения были локализованы и проверяемы метриками.

### Контекст цели
|      Параметр      | Описание                                                                                                                                                                                                                                                                                                   |
|:------------------:|:-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
|  Текущая проблема  | Фрагментированная логика промо в коде и пакетах Oracle создаёт bus-factor и нагрузку на базу данных. Отсутствие единой модели статусов приводит к эскалациям поддержки. Прямые интеграции через общие таблицы БД создают скрытую связанность                                                               |
|  Кого затрагивает  | Клиенты (оформление заказа), поддержка (эскалации статусов), аналитика (расхождение данных), бизнес (скорость вывода промо)                                                                                                                                                                                |
| Желаемое изменение | Изоляция промо-механик в отдельный микросервис с fallback-логикой и событийным обменом. Введение Anti‑Corruption Layer (ACL) для партнёрских интеграций. Создание read-модели истории заказов (Order Timeline), обогащаемой событиями от промо-сервиса. Снижение нагрузки на OLTB за счёт выноса аналитики |
| Горизонт изменений | Первый релиз (MVP трансформации); квартал                                                                                                                                                                                                                                                                  |
|  Ожидаемый эффект  | Снижение bus‑factor; снятие прямой нагрузки с базы данных; создание фундамента для event‑driven прослеживаемости заказов; снижение операционных рисков                                                                                                                                                     |

## 8. Целевая архитектура первого этапа
### Краткое описание TO-BE
Платформа сохраняет Java-монолит и ORACLE OLTB как владельца авторитарного состояния заказа (authoritative write model).
Ядро оформляет заказы по текущему critical path, используя fallback-логику скидок при недоступности внешнего сервиса.

Мы создаём вокруг ядра безопасный контур (safe seams), который обеспечивает параллельное существование старого и нового 
контуров без остановки бизнеса:
* Промо-сервис публикует события OrderDiscounted через Event Backbone; монолиту доступен fallback
* .NET Integration переведён на JMS-сообщения вместо записи в общую таблицу (INT_ORDER_EXPORT)
* Появляется read‑модель истории заказов (Order Timeline) на событиях от промо-сервиса и других источников
* Аналитика переключается на изолированный read-контур (Analytical Store); нагрузка direct SQL access на OLTP снижается
* Для одного пилотного партнёра вводится Integration Facade / Partner Adapter для нормализации протокола

На этом этапе ядро checkout, payment orchestration и operational data остаются в монолите/Oracle. Новые компоненты 
строят производные проекции (read models) и контрактные границы, не создавая второго источника истины.
