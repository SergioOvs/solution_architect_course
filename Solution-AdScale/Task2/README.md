# Task 2. Проектирование RTB и интеграции с DSP
Директория: Solution-AdScale/Task2

## Цель
Разработка архитектуры высоконагруженного RTB-сервиса для подключения новой DSP-платформы с жесткими требованиями 
к производительности и отказоустойчивости.

<b>Ключевые показатели (SLA):</b>
* <b><i>Задержка (Latency):</i></b> P95 не более 100 мс (целевой показатель для нового партнёра — 80 мс).
* <b><i>Пропускная способность (RPS):</i></b>
  * 18 000 запросов в секунду — через 3 месяца.
  * 50 000 запросов в секунду — через 12 месяцев.

5. `reliability.md` — паттерны надежности

## Краткий обзор
Критический путь обработки RTB-аукциона (hot path) реализован на базе gRPC с передачей дедлайнов (deadline propagation)
по цепочке: DSP API Gateway => Ad Server => Bidding Service => Delivery Service.

Для соблюдения жестких требований по задержкам Bidding Service в синхронном треке не обращается к PostgreSQL, используя 
исключительно Redis для чтения конфигурации и бюджетных лимитов.

Логирование событий (показы, клики, результаты аукциона win/loss) вынесено в асинхронный поток: публикация в Kafka 
происходит после отправки ответа пользователю.

Надежность системы обеспечивается тремя уровнями защиты:
* <i>Circuit Breaker:</i> на каждом вызове внешней зависимости для предотвращения каскадных сбоев.
* <i>Резервные стратегии (Fallback):</i> использование кэшированных данных в Redis или дефолтных ставок при недоступности основных сервисов.
* <i>Идемпотентность:</i> строгая гарантия однократной обработки финансовых операций (списаний бюджета).
