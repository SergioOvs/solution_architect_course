# API gateway. Дизайн для интеграций с DSP-партнерами
## Назначение
DSP API Gateway выступает в роли единой точки входа (Entry Point) для всего входящего RTB-трафика. Он принимает bid 
requests от DSP-партнёров по протоколу OpenRTB, выполняет аутентификацию, управляет нагрузкой (rate limiting), 
обеспечивает безопасность периметра и маршрутизирует запросы к Ad Server.

Выступая в качестве архитектурного фасада (в рамках паттерна Strangler Fig), Gateway полностью изолирует внутренние 
сервисы от прямого взаимодействия с внешним миром. Это позволяет независимо развивать, масштабировать и изменять 
внутренние протоколы, топологию микросервисов или версии OpenRTB, не нарушая контракт со стороны DSP-партнёров.

## Технология
В роли API Gateway используется Envoy Proxy. Поскольку полностью удовлетворяет критериям:
* Встроенные паттерны отказоустойчивости: декларативная конфигурация без изменения кода сервисов для rate limiting 
(на уровне глобального RPS и по ключам), circuit breaking (лимиты соединений, запросов и пулов), автоматических retry 
с определением таймаутов и попыток, а также outlier detection для изоляции нестабильных инстансов
* Производительность: экстремально низкая собственная latency (overhead Envoy составляет 1–3 мс), что гарантирует 
соблюдение жесткого требования к сквозной задержке (end-to-end) в пределах <= 80 мс.
* Богатая наблюдаемость (Observability): из коробки доступны метрики в формате Prometheus (latency, RPS, статусы 
ответов), распределённый трейсинг и гибко настраиваемые access logs (JSON) для детального аудита трафика.
* Нативная поддержка протоколов: полная поддержка HTTP/2 и нативное gRPC-проксирование для внутреннего контура, а также 
встроенный gRPC-JSON transcoding, позволяющий принимать HTTP/JSON от внешних клиентов и прозрачно транслировать их 
во внутренние gRPC-сервисы
* Нативная интеграция с Kubernetes: автоматическое обнаружение сервисов (Service Discovery) через xDS API и 
Kubernetes API, поддержка Ingress, Gateway API и ExternalName-сервисов, что исключает необходимость ручной перезагрузки 
конфигурации при масштабировании
* Управление конфигурацией: декларативная настройка через статические YAML/JSON файлы или динамическое управление через
Control Plane (например, Istio Pilot), что позволяет версионировать настройки и применять их с нулевым временем простоя 
(hot restart)
* Производительность на gRPC: Envoy демонстрирует подходящий overhead и более предсказуемую задержку при высококонкурентных
потоках HTTP/2
* Единый стек: возможность использовать Envoy как для внешнего ingress-трафика, так и для sidecar-контейнеров в 
service mesh, что унифицирует эксплуатационные метрики и логику работы всей инфраструктуры

## Маршрутизация

| «Ручка»                | Назначение                                                |     Upstream-сервис      |
|:-----------------------|:----------------------------------------------------------|:------------------------:|
| GET  /health           | Health check Gateway для балансировщика партнёра          | Локальный статус Gateway |
| POST /openrtb/v2.5/bid | Приём ставки (bid request) от DSP-партнёра (стандарт 2.5) |        Ad server         |
| POST /openrtb/v3.0/bid | Приём ставки (bid request) от DSP-партнёра (стандарт 3.0) |        Ad server         |


<b>Трансляция протокола: OpenRTB => REST или gRPC</b>

Поскольку DSP-партнёры взаимодействуют через стандарты OpenRTB 2.5 или 3.0 (JSON), Gateway выступает в роли транслятора
и выполняет следующие операции перед передачей данных в Ad server:
* <b><i>Валидация схемы:</i></b> проверка наличия обязательных полей OpenRTB (id, imp, app/site) и корректности типов данных. 
Некорректные запросы отклоняются на входе.
* <b><i>Нормализация:</i></b> приведение входящих данных к единому каноническому формату. Это позволяет внутреннему Ad server работать
со стабильной структурой, не поддерживая различия между версиями OpenRTB 2.5 и 3.0.
* <b><i>Обогащение метаданными:</i></b> внедрение в тело запроса или контекст служебной информации: идентификатора партнёра (извлеченного
из API-ключа), точного времени приёма запроса (ingress timestamp) и сквозного идентификатора трейса (trace ID).
* <b><i>Проксирование:</i></b> передача подготовленного запроса во внутренний контур. В зависимости от реализации Ad server используется 
либо HTTP/JSON, либо бинарный gRPC-протокол.

## Rate лимиты
Нужен для защиты внутренних сервисов от перегрузки и обеспечения распределения квот между партнерами.

<b>Параметры ограничения:</b>
* Глобальный лимит - 20 000 RPS
* На партнера - индивидуальные лимиты RPS

<b>Алгоритм:</b>
Выбран Token bucket так как допускает кратковременные всплески, что подходит для профиля RTB-трафика.

<b>Ответ при превышении лимитов:</b>
Возвращает статус код `429 Too Many Request` c заголовками: `X-RateLimit-Limit`, `X-RateLimit-Remaining`, 
`X-RateLimit-Reset` и `Retry-After`.

## Аутентификация
Для аутентификации всех DSP-партнёров используется механизм API-ключей
<b>Основные принципы:</b>
* Идентификатор партнёра передаётся в заголовке X-DSP-API-Key, значение которого API Gateway сверяет с локальным кэшем.
Кэша обновляется раз в 60 секунд путём синхронизации с центральным конфигурационным хранилищем.
* В случае отсутствия заголовка или предоставления невалидного ключа Envoy немедленно обрывает соединение, возвращая 
статус 401 Unauthorized и блокируя дальнейшую передачу запроса на бэкенд.
* Для обеспечения повышенной безопасности в будущем предусмотрен переход на mTLS, при котором API-ключ будет 
использоваться как второй фактор, а первичная аутентификация будет осуществляться на основе взаимной проверки клиентских
TLS-сертификатов.
* При кэшировании используется TTL (Time To Live) в 60 секунд с последующей ленивой (on-demand) фонововой инвалидацией,
что гарантирует доступность новых ключей в течение минуты после их выпуска.
* Логика проверки ключей полностью реализована на уровне фильтров Envoy, что исключает передачу неавторизованного
трафика в сервисную сеть и обеспечивает задержку обработки менее 1 мс.
* Для аудита все попытки доступа с неверным или отсутствующим ключом логируются с указанием `x-request-id`, 
IP-адреса источника и дескриптора партнёра.
* Лимиты на количество запросов (rate limit), логика размыкателя цепи (circuit breaker) и сбор телеметрии (метрики) 
изолированы и рассчитываются индивидуально для каждого партнёра
* В рамках API Gateway одному API-ключу всегда соответствует ровно один DSP-партнёр

## Circuit breaker
Механизм Circuit Breaker выполняет двустороннюю защиту: он предотвращает зависание запросов к DSP-партнёру при сбоях 
Ad server, а также оберегает Ad server от повторного обрушения при резком наплыве накопившегося трафика.

<b>Состояния:</b>
Closed => Open => Half-Open => Closed
* <i>Closed (Закрыто / Норма):</i> трафик направляется к Ad server в штатном режиме. Circuit breaker прозрачно 
проксирует запросы, непрерывно подсчитывая долю ошибок и задержки (P95) в скользящем окне. Для принятия решения об 
открытии цепи анализируются данные за последние 10 секунд. Переход в состояние Open происходит только в том случае, если
за это окно было обработано минимум 100 запросов и при этом доля ошибок превысила 55% либо 95-й перцентиль задержек 
(P95) поднялся выше 120 мс.
* <i>Open (Открыто / Изоляция):</i> при превышении порога ошибок цепь размыкается. Ad server признается недоступным. 
Gateway мгновенно прерывает цикл, возвращая клиенту `503 Service Unavailable` без обращения к апстриму. В ответ 
добавляется заголовок `Retry-After: 5`, сигнализирующий о времени ожидания до следующей попытки. Состояние фиксируется 
в метрике `gateway_circuit_breaker_state{partner_id, state="open"}`, а в систему мониторинга отправляется алерт.
* <i>Half-Open (Полуоткрыто / Тестирование):</i> по истечении таймера изоляции в 5 секунд цепь переходит в тестовый 
режим. Gateway пропускает к Ad server строго ограниченное количество пробных запросов (5 probe-запросов). Если 80% этих 
пробных запросов (4 из 5) завершаются успешно, цепь считается восстановившейся и переходит в состояние Closed. 
Если же доля успешных ответов ниже 80% или получена хотя бы одна фатальная ошибка, система немедленно возвращается
в состояние Open с обновлением заголовка `Retry-After`.
* <i>Closed (Возврат в норму):</i> после успешного прохождения тестов в состоянии Half-Open счетчики ошибок и таймеры 
сбрасываются, и gateway возобновляет полную передачу трафика на Ad server в штатном режиме.

## Мониторинг времени отклика
Контроль задержек (latency) на уровне Gateway является критически важным, поскольку именно по этим показателям 
DSP-партнёры рассчитывают соблюдение SLA и начисляют штрафы. Для обеспечения полной прозрачности и локализации проблем
мониторинг строится на нескольких уровнях:

1. <b>Метрики Prometheus и перцентили</b>
Gateway собирает и экспортирует детализированные метрики latency для каждого 
DSP-партнёра и каждого маршрута с помощью Prometheus-гистограмм. Это позволяет отслеживать время ответа по перцентилям 
(P50, P95, P99).

|              Метрика              |    Тип    | Лейблы                         | Описание                                                                          |
|:---------------------------------:|:---------:|:-------------------------------|:----------------------------------------------------------------------------------|
| gateway_request_duration_seconds  | Histogram | partner_id, status_code, route | Latency полного цикла запроса: от получения на Gateway до отправки ответа клиенту |
|      gateway_requests_total       |  Counter  | partner_id, status_code        | Общее количество обработанных запросов                                            |
|   gateway_rate_limit_hits_total   |  Counter  | partner_id                     | Количество запросов, отклонённых по причине срабатывания rate limit               |
|   gateway_circuit_breaker_state   |   Gauge   | partner_id                     | Текущее состояние цепи: 0=CLOSED, 1=HALF-OPEN, 2=OPEN                             |
| gateway_upstream_duration_seconds | Histogram | upstream, status_code          | Время, затраченное непосредственно на обращение к Ad server (Bidding)             |


2. <b>Покомпонентный тайминг и трейсинг</b>
Для точной локализации источника задержки собирается покомпонентный тайминг (время внутри Gateway, время Bidding, время 
Delivery). Распределённый трейсинг (OpenTelemetry/Jaeger) обеспечивает сквозную видимость прохождения bid request через
всю цепочку: Gateway => Bidding => Redis/Delivery => Kafka-publish.

3. <b>Бизнес-метрики и насыщение</b>
Параллельно отслеживаются операционные показатели: доля ответов `no-bid`, `timeout`, `429` и `5xx`, общий RPS и уровень 
насыщения пулов соединений.

4. <b>SLO и упреждающие алерты</b>
Система мониторинга настроена на проактивное обнаружение деградации до того, как она приведёт к штрафам по SLA:
* <b><i>Латентность:</i></b> критический алерт срабатывает, если P95 времени ответа превышает 80 мс в течение 1 минуты,
что позволяет инженерам отреагировать до фиксации нарушения SLA.
* <b><i>Ошибки:</i></b> предупреждение активируется при росте доли ошибок `5xx` выше 1% за 5-минутное окно. Для контроля
темпа изменений используется калькуляция ошибок под целевой SLA 99.9%.
* <b><i>Отказоустойчивость:</i></b> мгновенный критический алерт при переходе circuit breaker в состояние `OPEN` 
(значение метрики `2`), сигнализирующий о полной изоляции апстрима.

Список алертов:

| Алерт                                           | Степень критичности | Задержка при срабатывании |
|:------------------------------------------------|:-------------------:|:-------------------------:|
| P95 latency превышает 80 ms для любого партнёра |      critical       |            1m             |
| Error rate выше 1% за последние 5 минут         |       warning       |            2m             |
| Circuit breaker открылся                        |      critical       |            0s             |


## Отказоустойчивость и масштабирование
<b><i>Резервирование:</b></i> для обеспечения непрерывности сервиса Gateway разворачивается как минимум в двух 
идентичных репликах под управлением HPA (Horizontal Pod Autoscaler) в Kubernetes.

<b><i>Автомасштабирование:</b></i> HPA динамически увеличивает количество реплик при достижении пороговых значений 
нагрузки — загрузки CPU свыше 70% или трафика на уровне 80% от установленного rate limit.

<b><i>Stateless-архитектура:</b></i> все реплики Gateway являются полностью идентичными и не хранят локального 
состояния. Для синхронизации счетчиков rate limit между инстантами используется внешнее хранилище Redis, что позволяет 
любому поду обрабатывать любой запрос.

<b><i>Внешний Healthcheck:</b></i> эндпоинт `/health` возвращает `200 OK` только при условии успешного соединения 
с upstream Ad server. Если Ad server недоступен или отвечает ошибкой, `/health` возвращает `503 Service Unavailable`, 
исключая проблемный под из балансировки нагрузки.
