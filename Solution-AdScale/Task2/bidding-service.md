# Спецификация Bidding service
## Назначение
Bidding service — это выделенный микросервис, обрабатывающий bid request от DSP-партнёров, который становится первым
доменом, выделяемым из монолита AdScale (см. Task1/adr/ADR-002).

Данный компонент является критичным по задержкам (latency-critical) узлом RTB-пути. Он принимает от Ad Server список 
кандидатов рекламы, применяет бизнес-правила взвешивания ставок и определяет победителя аукциона. Именно от скорости
и стабильности работы Bidding Service напрямую зависят win rate платформы и выполнение SLA перед DSP-партнёрами: 
P95 latency не должен превышать 100 мс при целевом значении около 80 мс.

## Границы сервиса
Bidding Service — это самостоятельный Bounded Context, выделенный из монолита AdScale, который инкапсулирует всю логику 
проведения RTB-аукциона.

<b>Что входит в Bidding Service:</b>
* <b><i>Приём и обработка:</i></b> получение списка кандидатов рекламы от Ad Server.
* <b><i>Бизнес-логика:</i></b> применение правил взвешивания (bid multipliers), проверка минимальной (floor price) и максимальной (bid_ceiling) ставок, а также ограничение частоты показов (frequency cap).
* <b><i>Контекстуализация:</i></b> динамическое изменение ставок на основе параметров конкретного показа.
* <b><i>Финансы:</i></b> проверка доступного бюджета кампании через синхронный запрос к Budget Service.
* <b><i>Логика аукциона:</i></b> выбор победителя по настраиваемому алгоритму (First Price или Second Price).
* <b><i>Интеграция:</i></b> публикация события bidding.bid_won.v1 в Kafka и возврат bid response с данными победителя в Delivery Service.

<b>Что не входит в Bidding Service:</b>
* <b><i>Подбор кандидатов:</i></b> формирование списка релевантных объявлений — это ответственность Ad Server.
* <b><i>Креативы:</i></b> формирование HTML/JS-разметки баннера и трекинговых пикселей — это ответственность Delivery Service.
* <b><i>Управление кампаниями:</i></b> настройка ставок, таргетингов и стратегий — это ответственность Campaign Service.
* <b><i>Финансовые операции:</i></b> управление балансами, списание средств и инвойсинг — это ответственность Financial Service.
* <b><i>Аналитика:</i></b> хранение, агрегация и отображение статистики — это ответственность Statistics Service.

## API
Для обеспечения строгих требований к задержкам (P95 ≤ 100 мс) Bidding Service использует gRPC. Выбор протокола 
обусловлен бинарной сериализацией Protobuf (быстрее JSON), мультиплексированием HTTP/2 (без накладных расходов 
на установку соединения для каждого запроса) и строгой типизацией контрактов, минимизирующей ошибки интеграции.

### 1. Интерфейс сервиса
|  Метод   | Назначение                                                               |
|:--------:|:-------------------------------------------------------------------------|
| Evaluate | Взвешивание ставок, применение бизнес-правил и выбор победителя аукциона |

### 2. Контракт
```protobuf
syntax = "proto3";

package bidding.v1;

// Сервис принятия решений по ставкам в реальном времени
service BiddingService {
  // Оценивает кандидатов, применяет бизнес-правила и определяет победителя
  rpc Evaluate(EvaluationRequest) returns (EvaluationResponse);
}

// Входящий запрос на оценку аукциона
message EvaluationRequest {
  string auction_id      = 1; // Уникальный ID аукциона (для идемпотентности и трейсинга)
  string profile_id      = 2; // Идентификатор профиля пользователя
  ImpressionContext ctx  = 3; // Контекст показа
  repeated BidCandidate bids = 4; // Список ставок от Ad Server
}

// Контекст рекламной импрессии
message ImpressionContext {
  string publisher_id    = 1; // Сайт или приложение
  string slot_id         = 2; // Конкретное рекламное место
  string country         = 3; // География пользователя
  string platform        = 4; // Устройство (desktop, mobile, tablet)
  int64  event_timestamp = 5; // Unix timestamp в миллисекундах
}

// Кандидат на участие в аукционе
message BidCandidate {
  string campaign_ref    = 1; // Ссылка на кампанию
  string creative_ref    = 2; // Ссылка на объявление (креатив)
  double base_cpm        = 3; // Базовая ставка (CPM, USD)
  double min_acceptable  = 4; // Минимально допустимая ставка (floor)
}

// Ответ сервиса с результатом торгов
message EvaluationResponse {
  string auction_id      = 1;
  BidOutcome outcome     = 2;
  WinningBid winner      = 3; // Заполняется только при outcome = SUCCESS
}

// Запрос на атомарное резервирование бюджета 
message ReserveBudgetRequest { 
  string campaign_id = 1; // Идентификатор кампании для списания 
  double amount = 2; // Сумма к резервированию (рассчитанная итоговая ставка / bid)
  string idempotency_key = 3; // Ключ идемпотентности для защиты от дублей
} 

// Ответ от сервиса бюджета
message ReserveBudgetResponse {
  bool success = 1; // true, если бюджет зарезервирован
  string reason = 2; // Причина отказа (например, INSUFFICIENT_FUNDS)
} 

// Сервис бюджета (внутренний контракт Bidding <-> Budget)
service BudgetService {
  // Атомарно резервирует бюджет. Возвращает 200 OK или 409 Conflict. 
  rpc ReserveBudget(ReserveBudgetRequest) returns (ReserveBudgetResponse);
}

// Возможные исходы обработки запроса
enum BidOutcome {
  SUCCESS       = 0; // Победитель определён
  REJECTED      = 1; // Никто не прошёл фильтры или бюджет исчерпан
  DEADLINE_HIT  = 2; // Превышен внутренний таймаут сервиса
  FAILURE       = 3; // Внутренняя системная ошибка
  CLIENT_CANCEL = 4; // Отмена инициатором (deadline exceeded на клиенте)
}

// Данные выигравшей ставки
message WinningBid {
  string campaign_ref    = 1;
  string creative_ref    = 2;
  double adjusted_cpm    = 3; // Итоговая ставка после применения множителей
  double clearing_cpm    = 4; // Финальная цена клиринга (Second Price)
}

```

### 3. SLA по таймаутам
Bidding Service обязан вернуть ответ строго до истечения клиентского дедлайна. При нехватке времени сервис возвращает 
ResponseStatus.TIMEOUT.

|      Вызывающая сторона       | Дедлайн на вызов | Обоснование                                                                                                 |
|:-----------------------------:|:----------------:|:------------------------------------------------------------------------------------------------------------|
|  Ad Server (внутренний RTB)   |      50 мс       | Оставляет запас для дальнейшей цепочки (проверка бюджета, запись в Kafka) в рамках общего бюджета 80–100 мс |
| API Gateway (внешний OpenRTB) |      60 мс       | Соответствует типичным SLA внешних партнёров                                                                |

### 5. Операционные требования
* Идемпотентность: Поле auction_id используется для дедупликации повторных запросов.
* Трейсинг: auction_id пробрасывается через все сервисы цепочки для сквозной отладки в Jaeger/Zipkin.
* Версионирование: Пакет bidding.v1 позволяет вносить изменения в будущем без нарушения обратной совместимости.

## Зависимости
|    Компонент     |    Протокол    | Роль                                                                                                              | Стратегия при сбое                                                                                                                        |
|:----------------:|:--------------:|:------------------------------------------------------------------------------------------------------------------|:------------------------------------------------------------------------------------------------------------------------------------------|
|  Redis Cluster   | Redis protocol | Горячее чтение данных: множители ставок (bid multipliers), минимальные цены (floor prices), конфигурация кампаний | Переход на BiddingDB с ростом задержки (latency)                                                                                          |
|  Budget Service  |      gRPC      | Атомарное резервирование бюджета перед выбором победителя                                                         | Использование закэшированных лимитов из Redis (TTL 5с) при недоступности Budget Service (с последующим reconciliation при восстановлении) |
|    BiddingDB     |    SQL / KV    | Бизнес-правила в рантайме, индексы ставок                                                                         | Чтение из кэша Redis; при недоступности кэша — NO_BID                                                                                     |
|      Kafka       | Async producer | Логирование событий победы или проигрыша в аукционе (win/loss)                                                    | Буферизация на стороне producer (fire-and-forget)                                                                                         |
| Campaign Service |      gRPC      | Получение актуальных данных при промахе кэша (cache miss)                                                         | Использование устаревшего кэша в рамках заданного TTL                                                                                     |

<b>Архитектурное ограничение hot path</b>
В синхронном треке обработки ставки (hot path) отсутствуют запросы к Legacy PostgreSQL. Это фундаментальное ограничение 
архитектуры, которое гарантирует соблюдение целевого перцентиля задержки P95 ≤ 100 мс. Любые тяжелые или не гарантирующие
SLA операции вынесены за пределы критического пути.
