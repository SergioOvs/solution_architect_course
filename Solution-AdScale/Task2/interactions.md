# Схема взаимодействия
В архитектуре AdScale все взаимодействия строго классифицируются на три категории в зависимости от их критичности 
для бизнеса и требований к производительности:
1. <b><i>RTB hot path (Критический путь аукциона):</i></b> синхронные вызовы, определяющие скорость прохождения 
bid request. Это самый приоритетный контур, где действует жесткое требование к задержкам: P95 <= 100 мс end-to-end. 
Любая деградация в этом канале напрямую конвертируется в потерянные аукционы и снижение выручки.
2. <b><i>Domain calls (Доменные операции):</i></b> синхронные запросы к вспомогательным сервисам для управления кампаниями, финансами и аналитикой. Здесь допускаются мягкие требования к latency, а ключевыми приоритетами выступают надежность, транзакционная целостность и корректность данных.
3. <b><i>Event streaming (Асинхронный поток событий):</i></b> обработка показов, кликов и результатов аукционов через брокеры сообщений (Kafka). Этот канал полностью отделен от синхронного RTB-пути и физически не может блокировать его выполнение, обеспечивая слабую связанность (loose coupling) системы.

## RTB hot path (Критический путь аукциона)
Для синхронной коммуникации в критическом RTB-пути 
(цепочка: API Gateway => Ad Server => Bidding Service => Delivery Service) выбран протокол gRPC (HTTP/2 + Protobuf). 
При нагрузке в 50 000 RPS бинарная сериализация и особенности транспортного уровня дают существенный выигрыш в latency 
по сравнению с REST/JSON.

|      Критерий      | gRPC (Выбранный стек)                                                                             | REST/JSON                                                                            |                                                                                                                                                           
|:------------------:|:--------------------------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------|
|    Сериализация    | Protobuf: бинарный формат, высокая скорость парсинга и минимальный объем данных                   | JSON: текстовый формат, требует больше CPU и пропускной способности                  |                                     
|     Транспорт      | HTTP/2: мультиплексирование потоков в одном TCP-соединении, эффективное сжатие заголовков (HPACK) | HTTP/1.1: зависимость от пулов соединений или overhead на установку новых TCP-сессий |  
|      Контракт      | .proto-файлы: строго типизированный IDL, исключающий ошибки несовпадения схем на этапе компиляции | OpenAPI: декларативное описание, допускающее нестрогую типизацию полей               |                
| Задержки (Latency) | Минимальные: за счет бинарного протокола и отсутствия блокировок на уровне TCP                    | Повышенные: из-за текстовой сериализации и ограничений HTTP/1.1                      |                                          
| Потоки (Streaming) | Нативная поддержка: двусторонний (bidirectional) streaming из коробки                             | Сложная реализация: требует надстроек (WebSocket, SSE)                               |                                                            

Управление таймаутами (Propagation Deadline) Ключевым преимуществом gRPC является встроенная поддержка дедлайнов. 
Дедлайн (deadline), установленный на входе в API Gateway, автоматически распространяется (propagates) через заголовки 
grpc-timeout во все нижестоящие синхронные вызовы.

Это предотвращает «эффект ожидания в пустоту»: если общий лимит времени на обработку bid request исчерпан, нижестоящие 
сервисы (например, Bidding Service) не будут тратить ресурсы на обращение к Ad Server, заведомо зная, что ответ уже не
успеет вернуться в окно SLA.

## Domain calls (Доменные операции)

Для взаимодействия Advertiser Dashboard с Campaign Service, Financial Service, Analytics Service, Budget Service выбран 
архитектурный стиль REST (HTTP/1.1 или HTTP/2 + JSON).

В отличие от RTB hot path, данные вызовы (domain calls) не требуют экстремально низкой задержки (P95 <= 100 мс), 
так как представляют собой CRUD-операции: создание рекламных кампаний, управление бюджетами и формирование отчётности.

<b>Обоснование выбора:</b>

|        Критерий         | Преимущество REST/JSON для доменных вызовов                                                                                                          |
|:-----------------------:|:-----------------------------------------------------------------------------------------------------------------------------------------------------|
|      Совместимость      | Нативная поддержка во всех браузерах и легковесная интеграция с внешними системами без необходимости внедрять gRPC-клиенты                           |
|  Отладка и разработка   | Текстовый формат JSON легко читается человеком, что упрощает диагностику через прокси (Charles/Fiddler) и логи                                       |
| Контракт и документация | OpenAPI-спецификации (Swagger) интуитивно понятны не-техническим участникам (менеджерам, поддержке, партнерам), в отличие от бинарных .proto-файлов  |
|  Требования к скорости  | Для административных и аналитических задач latency в 200–500 мс является приемлемым, что делает накладные расходы JSON допустимой платой за гибкость |

## Event streaming (Асинхронный поток событий)

Для потоковой передачи событий показов, кликов и биллинга выбран <b>Apache Kafka</b>. В отличие от синхронных вызовов или классических очередей (например, RabbitMQ), Kafka выступает в роли распределённого отказоустойчивого журнала событий (commit log), что идеально подходит для развязывания RTB-пути от фоновой обработки.

<b>Обоснование выбора архитектуры:</b>

* <b><i>Неблокирующая публикация (Fire-and-forget):</i></b> сервисы-источники (Delivery Service, Bidding Service) 
записывают событие в топик и немедленно возвращают ответ пользователю. Обработка события не входит в критический путь 
(latency path) и не влияет на пороговые значения RTB.
* <b><i>Развязка производителей и потребителей:</i></b> Kafka позволяет множеству независимых сервисов 
(Statistics, Analytics, Financial) потреблять один и тот же поток данных через разные consumer groups. Это исключает 
необходимость дублировать отправку событий для каждой системы.
* <b><i>Буферизация пиковой нагрузки:</i></b> при резких всплесках трафика события надёжно сохраняются в логе Kafka. 
Консьюмеры обрабатывают их в собственном темпе, что защищает нижестоящие базы данных от перегрузки и деградации.
* <b><i>Гарантированная доставка и воспроизводимость (Replayability):</i></b> обеспечивается доставка at-least-once
с хранением данных в течение 7 дней. Это критически важно для корректности биллинга: при сбое в Statistics Service или 
изменении логики агрегации данные можно переиспользовать для перестроения отчётов (replay).
* <b><i>Масштабируемость и порядок событий:</i></b> партиционирование по ключу (например, campaign_id) позволяет 
горизонтально масштабировать нагрузку, сохраняя при этом строгий порядок событий внутри одной рекламной кампании.

<b>Контур данных:</b>

Producers: Delivery Service, Bidding Service, Financial Service.
Consumers: Statistics Service, Analytics Service, Financial Service.

## Необходимость API Gateway

<b>Вывод:</b> Внедрение DSP API Gateway как отдельного инфраструктурного компонента является обязательным.

<b>Обоснование:</b>

* <b><i>Централизация ответственности и соблюдение SLA:</i></b> Новый DSP-партнёр устанавливает жесткие требования 
к задержкам (P95 <= 80 мс) и вводит штрафные санкции. Gateway обеспечивает единый слой наблюдаемости (latency metrics)
и защиты (circuit breaker) на границе сети, предотвращая деградацию апстрима (Ad Server/Bidding Service).
* <b><i>Абстракция и трансляция протоколов:</i></b> Внешние партнёры используют OpenRTB (JSON/HTTP), в то время 
как внутренняя архитектура строится на gRPC/Protobuf. Gateway берет на себя трансляцию и адаптацию контрактов, изолируя
внутреннюю топологию от внешних изменений.
* <b><i>Периметральная безопасность:</i></b> Функции аутентификации по API-ключам, rate limiting и защиты от DDoS должны
выполняться на входе, отсекая невалидный трафик до того, как он нагрузит бизнес-логику сервисов.
* <b><i>Масштабируемость (Multi-tenancy):</i></b> Архитектура рассчитана на подключение нескольких DSP-площадок 
в течение года. Gateway выступает единым ingress'ом, обеспечивая маршрутизацию и применение политик на уровне 
конкретного партнёра.
* <b><i>Основа для рефакторинга (Strangler Fig):</i></b> Gateway служит стабильным фасадом, за которым могут 
одновременно работать старый монолит AdScale и новые микросервисы. Это позволяет переключать трафик постепенно 
и безопасно откатывать изменения.
* <b><i>Устранение дублирования:</i></b> Без единой точки входа каждая команда будет вынуждена реализовывать 
TLS-терминацию, rate limiting и observability внутри своих сервисов. Это ведет к рассогласованности политик 
и неэффективному расходу ресурсов.

Подробное описание см. в `api-gateway.md`.

# Описание взаимодействия
Sequence диаграмма: [interaction_seq.md](diagrams/interaction_seq.puml)

<b><i>Вход:</i></b> Запрос поступает от DSP-партнёра или пользователя сайта по протоколу HTTPS (OpenRTB).<br>
<b><i>API Gateway:</i></b> Первая точка входа. Выполняет аутентификацию, применяет rate limiting и Circuit Breaker 
к вышестоящим сервисам. Передаёт запрос на Ad Server по HTTP/gRPC.<br>
<b><i>Ad Server:</i></b> Идентифицирует пользователя и подбирает список кандидатов (Ad Candidates). Для быстрого доступа
к профилям таргетинга и конфигурациям кампаний читает данные из Redis. Устанавливает дедлайн (deadline propagation) 
для следующего шага.<br>
<b><i>Bidding Service:</i></b> Получает список кандидатов по gRPC. Применяет множители ставок, проверяет доступный 
бюджет (через Redis fallback) и выбирает победителя. Возвращает результат Ad Server.<br>
<b><i>Delivery Service:</i></b> Формирует финальный HTML/JS-код баннера и отправляет HTTPS-ответ пользователю 
или DSP-партнёру.<br>
<b><i>Асинхронный трек (после ответа):</i></b> Сразу после отправки ответа пользователю Delivery Service 
(или Bidding Service) публикует события (показы, клики, результаты аукциона win/loss) в Kafka через 
Event processing service. Это гарантирует, что запись событий не блокирует критический путь пользователя.<br>
