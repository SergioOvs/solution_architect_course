# Архитектурные драйверы
## Функциональные требования

|  ID   | Требование                                                                                         | 
|:-----:|:---------------------------------------------------------------------------------------------------|
| FR-1  | Принимать bid-request в рамках текущих и новых интеграций с DSP партнеров по RTBOpen               |
| FR-2  | Отправлять корректный bid-response на bid-request в установленные SLA                              |
| FR-3  | Управление кампаниями, таргетингом, ставками и бюджетом должно быть доступно через ЛК пользователя |
| FR-4  | Инфообмен в рамках аналитики и сбора статистики должен быть выделен из RTB hot path                |
| FR-5  | Выполнять финансовые операции (списание, пополнение средств и выставление счета)                   |
| FR-6  | Пополнение бюджета должно быть через Платежный шлюз                                                |
| FR-7  | Иметь возможность подключения нескольких DSP                                                       |

## Атрибуты качества
|        Атрибут         | Описание                                                                                                                                                                                                                                   |                     Приоритет                      |
|:----------------------:|:-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:--------------------------------------------------:|
|   Производительность   | - Система должна выдерживать не менее 18 000 RPS для MVP и 50 000 RPS в целевом варианте<br>-P95 latency для RTB-потока не более 100ms<br>-Время отклика для нового DSP партнера не более 80ms                                             |                     Критичный                      |
|    Масштабируемость    | - Поддержка горизонтального масштабирования для нагруженных компонентов                                                                                                                                                                    |                     Критичный                      |
| Доступность/Надежность | - SLA в целевом решении 99,9%<br>- Деградация или отказ экземпляра Auction Engine не блокирует RTB<br>- БД не является SPoF <br>- Развертывание в нескольких регионах                                                                      |                     Критичный                      |
|      Безопасность      | - Для внешних систем установка rate limit и процесс аутентификации                                                                                                                                                                         |                      Средний                       |
|      Изменяемость      | - Поэтапное выделение сервисов из монолита<br>- Частые релизы и быстрый откат                                                                                                                                                              |                      Высокий                       |
|    Сопровождаемость    | - Нужны метрики, трейсы и логи на hot path для контроля исполнения SLA и штрафов<br>- Для всех сервисов: RPS, P95/P99 latency, Kafka lag, DB locks, error rate, timeout rate                                                               |                      Высокий                       |
| Согласованность данных | - Финансовые операции должны поддерживать транзакционность и идемпотентность<br>-Сбор статистики должен поддерживать eventual consistency и данные не должны теряться<br>- Допускается задержка в обновлении данных в аналитических данных | Высокий для фин. операций / Средний для статистики |

## Ограничения
### Бизнес-ограничения

|  ID  | Ограничение                                            |
|:----:|:-------------------------------------------------------|
| BL-1 | Срок: MVP - 3 месяца, целевое - 1 год                  |
| BL-2 | Ограниченный бюджет                                    |
| BL-3 | Подключение крупной DSP (прирост трафика +20%)         |
| BL-4 | Не должно прерываться обслуживание клиентов            |
| BL-5 | Изменения в UX/UI не должны привести к оттоку клиентов |

### Технические ограничения

|  ID   | Ограничение                                                     |
|:-----:|:----------------------------------------------------------------|
| TL-1  | Поэтапная миграция (Полностью и сразу переписать всю ИС нельзя) |
| TL-2  | Существующий стек: C++/Go/Python/Node                           |
| TL-3  | База данных: PostgreSQL (одна инстанция)                        |
| TL-4  | Отсутствует Кеш                                                 |
| TL-5  | Отсутствует MQ                                                  |
| TL-6  | Отсутствует контейнеризация и автоматизированный процесс CI/CD  |
| TL-7  | Ручной deploy                                                   |
| TL-8  | Один production-кластер                                         |
| TL-9  | Отсутствует документация                                        |
| Tl-10 | P95 времени отклика при аукционе не более 100ms                 |

### Организационные ограничения

|  ID  | Ограничение                                                                                                                                  |
|:----:|:---------------------------------------------------------------------------------------------------------------------------------------------|
| OL-1 | Команда 35 человек: 35 человек: backend-, frontend- и DevOps-разработчики, тестировщики, дизайнеры, сотрудники службы поддержки и менеджмент |
| OL-2 | Отсутствуют выделенные сотрудники: SRE-инженер, тех. писатель и бизнес-аналитик                                                              |
| OL-3 | У сотрудников должна быть экспертиза в выбранных технологиях или они легко и быстро осваиваются                                              |

## Ключевые архитектурные решения
Архитектурные решения, выведенные после изучения драйверов
1. Для переработки монолита использовать паттерн Strangler Fig
2. Первые компоненты для выделения из монолита - Bidding сервис, так как он влияет на выполнение SLA(избежание штрафов от партнера) и выручку
3. Разделить потоки ифнообмена: критичный RTB-поток и второстепенные потоки (статистика, аналитика, личный кабинет)
4. Добавить БД Redis для организации кеширования кампаний, ставок, таргетинга и быстрых бюджетных проверок
5. Добавить Kafka для буферизации запросов к БД для статистики
6. Добавить API Gateway c rate limit, авторизацией, circuit breaker и мониторинга для интеграций с DSP/
