# Целевая архитектура AdScale
## Описание целевого состояния
Через 1 год AdScale должна быть способна поддерживать не менее 50 000 RPS, SLA 99.9%, интеграции с множеством DSP, 
для latency критичных компонентов горизонтальное масштабирование, событийную обработку кликов и показов и разделение 
данных по сервисам. [C4 Container диаграмма целевой архитектуры](diagrams/to-be_container.puml)

Достижение целевого состояния предполагается решить с помощью MVP, который должен будет выведен через 3 месяца и призван
снизить риски при подключении нового DSP партнера путем разгрузки hot path, отделению наиболее нагруженных потоков и 
изоляции критических важных компонентов от статистики, аналитики и личного кабинета.

## Выбор архитектурного стиля
### Почему не оставить монолит
+ Монолит уже достиг своего придела
    + P95 latency выше установленных требований
    + Одна PostgreSQL инстанция для всех нагрузок
    + Event Streaming напрямую в production БД
    + Аналитика, RTB и финансовые операции конкурируют за ресурсы
+ Монолит масштабируется целиком. Отдельно нельзя масштабировать Auction Engine, Statistics Service и Analytics Service
+ Отсутствует изоляция отказов. Любой сбой бьет по основному бизнес процессу - Аукцион

### Почему не переписать монолит на микросервисы сразу
+ Срок 3 месяца для MVP (BL-1) и ограниченный бюджет (BL-2)
+ Высокие риски при эксплуатации планируемого количества сервисов, распределенных транзакций и service mesh без выделенного SRE (OL-2)
+ Отсутствие документации (TL-9) - разработка без четкого плана с высоким риском получить хорошее тех. решение без учета бизнес-потребностей
+ Ограниченный человеческий ресурс (OL-1) с риском деградации качества - необходимость в параллельной разработке микросервисов и сопровождению легаси монолита

### Выбор подхода для достижения целевого решения
|           Подход           | Описание                                                                                              | Плюсы                                                                                                                                                                                              | Минусы                                                                                                                                     |
|:--------------------------:|:------------------------------------------------------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|:-------------------------------------------------------------------------------------------------------------------------------------------|
|     Модульный монолит      | Определение и выделение модулей внутри монолита, уменьшение нагрузки на БД за счет репликаций         | Скорость, низкая цена, низкие операционные риски, "закладка" для перехода на микросервисы                                                                                                          | Нет возможности отдельного масштабирования критического компанента, нет изоляции потоков, объединеных сейчас в hot path                    |
| Монотонный распил монолита | По сервисное разделение монолита по доменам                                                           | Контролируемый процесс                                                                                                                                                                             | Отсутствие приоритезации - критически важные модули могут быть выведены в последнюю очередь, что повышвет риски для выполения SLA партнера |
|   Strangler Fig Pattern    | "Душенее" монолита путем вынесения сервисов согласно приоритетам сервисов (от критичного до низкого). | Приоритизация - в первую очередь выводятся критически значимые сервисы; плавный переход без остановки системы; снижение рисков - проблемный трафик можно вернуть на legacy; быстрый эффект для SLA | Требует обеспечивающей инфраструктуры; параллельная поддержка legacy функционала и новой реалиации                                         |

Вывод: Оптимальный подход - Strangler Fig Pattern, так как это позволит получить быстрый эффект для SLA и сохранить 
управляемый темп перехода от текущего состояние (монолит) к целевому состоянию (микросервисы).

## Архитектура MVP (через 3 месяца)

|     Компонент      | Описание                                                                                                         |
|:------------------:|:-----------------------------------------------------------------------------------------------------------------|
|    API Gateway     | Примем внешних запросов от DSP. Выполняет маршрутизацию, circuit breaker и auth; отслеживает rate limit          |
|  Bidding service   | Вынос из монолита latency критичного функционала для проведения Аукциона                                         |
|     Ad service     | Подключается чтение из кэш "горячих" данных (БД Redis). Исходный функционал не изменяется                        |
|  Delivery service  | Перевод с синхронного взаимодействия с БД на взаимодействие через буферизацию. Исходный функционал не изменяется |
|  Campaign service  | Логика остается в Legacy Монолите. Настроена Read-Replica для Bidding Service                                    |
|      БД Redis      | Подключается кэш для разгрузки hot path                                                                          |
|       Kafka        | Принимает события кликов и показов для дальнейшей записи в БД PostgreSQL                                         |
| Statistics service | Перерабатывается по паттерн асинхронный pipline                                                                  |
| Analytics service  | Перерабатывается по паттерн асинхронный pipline                                                                  |
|   Legacy Монолит   | Поддерживает работоспособность функционала, которые не изменяется в рамках MVP                                   |

## Основные этапы
### Промежуточное состояние. Через 3 месяца
<b>Цель:</b> Обеспечить P95 ≤ 100 мс для RTB-потока и подключить DSP-партнера без деградации SLA.
<b>Состав MVP:</b>
* <b><i>API Gateway:</i></b> Единая точка входа, rate limit, circuit breaker.
* <b><i>Bidding Service:</i></b> Выделен из Auction Engine. Владеет Bidding DB. В hot path использует Redis, к Legacy 
PostgreSQL обращается только при cache miss.
* <b><i>Legacy Monolith:</i></b> Сохраняет Ad Server, Delivery Service, Campaign/Budget/Financial логику и Dashboard.
* <b><i>Data Layer:</i></b>
  * <i>Bidding DB (PostgreSQL):</i> Master для Bidding Service.
  * <i>Campaign/Budget/Financial DB (PostgreSQL):</i> Read-Replica (или физически отдельные инстансы), обновляемые через
  CDC из Legacy PostgreSQL.
* <b><i>Statistics DB (ClickHouse):</i></b> Прием данных из Kafka.
* <b><i>Event Streaming:</i></b> Kafka Cluster для событий показов, кликов и аукциона.

<b>Порядок переноса и владельцы записи:</b>
<b><i>Недели 3–8:</i></b> Bidding Service становится владельцем записи в Bidding DB. Legacy Auction Engine переводится 
на чтение из Bidding DB.
<b><i>Недели 9–12:</i></b> Внедряется зеркалирование данных кампаний, бюджетов и финансов. Владельцем записи для этих 
доменов остается Legacy Monolith. Новые БД используются Bidding Service и Ad Server только в режиме чтения (Read-only).

### Целевое состояние. Через 1 год
* Поддержка 50 000 RPS, нескольких подключенных DSP-партнеров. 
* Горизонтальное масштабирование для API Gateway, Bidding service, Ad server, Delivery service и Event processing service
* Kafka для event streaming
* Данные разделены по сервисам
* Разделение транзакций и аналитики
* Обеспечен SLA 99.9%
* Есть контейнеризация сервисов и deploy/rollback через CI/CD
* Внедрен Service Mesh для межсервисного observability и retries.
* Обеспечено сквозное Observability (метрики, логи, трейсы, алерты) на всем hot path.
