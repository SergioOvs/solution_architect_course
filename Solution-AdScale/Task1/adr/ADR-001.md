# ADR-001: Стратегия эволюции архитектуры (от монолита к микросервисам)
|    Дата    | Статус  |
|:----------:|:--------|
| 18/09/2026 | Принята |

## Контекст
AdScale - гибридный монолит (Стек: C++ / Go / Python / Node) c единой для всех нагрузок БД PostgreSQL(1 инстанция). 
В монолите отсутствует кеш, очереди, контейнеризация. Деплой происходит в ручную, инфраструктура - 1 production-кластер
Текущее состояние AdScale характеризуется как предел возможностей:

|         Метрика          |         Значение         | Комментарий                                 |
|:------------------------:|:------------------------:|:--------------------------------------------|
|      Трафик, в пике      |        15 000 RPS        | Предельные показатели                       |
|       P95 latency        |        110–120 ms        | Явное нарушение требований. Норма <= 100 ms |
|  Запись в БД, нагрузка   |         Высокая          | Не запаса прочности                         |
|        Деградация        | Периодическая в часы пик | Риск перехода из периодической в постоянную |
| Запас производительности |       Отсутствует        | -                                           |

Необходимо подключить нового DSP-партнера, что должно увеличить нагрузку через 3 месяца до 18 000 RPS, а через 1 год до
50 000 RPS и SLA 99.9%

## Альтернативные варианты
### Вариант 1. Вертикальное масштабирование существующего монолита
<b>Плюсы:</b>
* Минимальные финансовые вложения на старте
* Минимальный перечень вносимых изменений на старте
* Скорость разработки
* Минимальное использование новых технологий

<b>Минусы:</b>
* Остается негативное влияние на latency, так как не убираются причины
* Отсутствие возможности независимого масштабирования Auction Engine
* Единая PostgreSQL DB - SPOF
* Высокий риск деградации после подключения новой DSP с прямым влиянием на риск получения штрафов

<b>Решение:</b> <b><i>Отклонено</i></b>. Высокий риск повторения текущей ситуации с latency, так как не устраняются 
причины.

### Вариант 2. "Шоковый" переход от монолита к микросервисам
<b>Плюсы:</b>
* Устранение первопричин негативного влияния на latency
* Сразу целевая архитектура
* Лучшее разделение доменов

<b>Минусы:</b>
* Долгий срок реализации
* На период разработки, остается работающий на пределе монолит
* Риск некорректного переноса бизнес логики из-за отсутствия документации
* Требуется выделенный SRE-специалист

<b>Решение:</b> <b><i>Отклонено</i></b>. Бизнес требует обеспечение не прерывности работы (BL-4). Есть ограничения 
срока (BL-1), бюджета (BL-2), человеческих ресурсов (OL-1, OL-2) и высокие операционные риски.

### Вариант 3. Модульный монолит
<b>Плюсы:</b>
* Скорость разработки
* Низкая стоимость
* Низкие операционные риски
* "Закладка" под микросервисную архитектуру

<b>Минусы:</b>
* Hot path конкурирует за ресурсы
* При растущих RPS нет способности к стабильной low latency
* Не решает проблему единой БД 

<b>Решение:</b> <b><i>Отклонено</i></b>. Не достаточно для обеспечения P95 на стабильном уровне в 100ms (TL-10)

## Решение
Использовать Strangler Fig Pattern для достижения целевого решения. Так как это обеспечит:
* Непрерывность бизнеса (BL-4). Суть паттерны заключается в том, что новое и легаси работают параллельно используя 
Gateway в качестве маршрутизатора.
* Ранний эффект для SLA. Изоляция hot path и добавление кэша оказывают положительное влияние на latency, что снижает 
риск получения штрафа от DSP-партнера 
* Удовлетворяет ограничениям: инкрементный подход укладывается в сроки (BL-1) и бюджет (BL-2); постепенный рост
количества сервисов, что приемлемо для команды, у которой есть ограничения в ресурсах (OL-1 и OL-2)
* Снижение и управление рисками. Инкрементный подход системы, у которой отсутствует документация, идет небольшими 
инкрементами со сверкой метрик и возможностью переключения на legacy функционал.

### Основные этапы 
MVP:
* добавить API Gateway перед новым внешним трафиком
* выделить Bidding Service как latency-критичный компонент
* добавить Redis для горячих данных в RTB-пути
* добавить Kafka для событий показов, кликов и события аукциона
* изолировать аналитику от production-БД через отдельный read/analytics контур
* сделать контейниризацию новых сервисов и добавить observability
* оставить legacy монолит только для функций, которые еще не мигрированы

Целевое решение:
* выделить Campaign Service, Budget Service, Statistics Service, Analytics Service и Financial Service;
* перейти к Database per Service;
* постепенно переводить внешний и внутренний трафик со старых функций на новые сервисы.


## Последствия
<b>Положительные:</b>
* Быстрый фокус на самом критичном bottleneck: RTB-аукционе
* Независимое масштабирование самых нагруженных сервисов
* Снижение нагрузки на PostgreSQL: добавление кэширования(Redis), очередей(Kafka) и replicas
* Поэтапное устранение связанности через общую БД и SPOF
* Непрерывность обслуживания клиентов
* Документирование системы параллельно разработке

<b>Отрицательные:</b>
* До достижения целевой архитектуры будет сосуществование legacy монолита и новых сервисов (Временное повышение 
нагрузки на команду)
* Увеличение затрат на инфраструктуру (Gateway, Redis, Kafka, replicas) (Дает снижение риска получения штрафов и потери
клиентской базы)
* На период сосуществование legacy монолита и новых сервисов потребуется управление согласованностью данных

## Критерии успеха
* Через 3 месяца после старта P95 latency для RTB-потока не превышает 100 ms при 18 000 RPS
* Через 1 год после старта P95 latency для RTB-потока не превышает 80 ms при 50 000 RPS
* Новый DSP-партнер успешно подключен с SLA 99.9%
* События кликов и показов больше не пишутся напрямую в production-БД в синхронном критичном потоке.
