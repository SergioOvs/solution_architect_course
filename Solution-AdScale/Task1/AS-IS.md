# Диагностика AS-IS состояния архитектуры AdScale
## Контекст
AdScale - это SaaS-платформа, которая позволяет пользователям-рекламодателям запускать рекламные кампании, управлять 
бюджетами и ставками, участвовать в аукционах в реальном времени (Real-Time Bidding, или RTB), показывать рекламу 
пользователям сайтов и приложений, а также собирать аналитику и формировать отчётность. Компания AdScale планирует 
интеграцию с крупной DSP-площадкой, что влечет повышения количества пользователей к концу года. В добавок, со стороны 
DSP-площадки действуют жесткие SLA: : стабильное время ответа не более 80 ms и штрафы за деградацию времени отклика 
(latency) и простои (downtime).

## Текущее состояние
AdScale реализованна как гибридный монолит, работающий на пределе своих возможностей.

<b>Цели бизнеса:</b>
Отдельно стоит учесть выставляемые бизнесом цели:
+ Рост нагрузки на 20% без деградации SLA
+ Трафик целевой 50 000 RPS для MVP не менее 18 000 RPS
+ MVP через 3 месяца
+ Целевое решение через 1 год
+ Разработка решения не должна нарушать ограничения: беспрерывная и стабильная работа, ограниченный бюджет, максимально
использовать текущий штат сотрудников 


## Узкие места
### 1. Единая БД для всех нагрузок
Основное узкое место. Один сервер обслуживает все потоки одновременно:
+ Hot path - синхронное чтение ставок и кампаний в Auction Engine
+ Event streaming - Statistics Service пишет кликии показы
+ Финансовые транзакции - Financial Service пишет транзакции и балансы
+ Тяжёлые аналитические, запросы отправляемые Analytics Service
+ CRUD операции от Advertiser Dashboard 

Это приводит к конкуренции за ресурсы БД. В дополнение тяжелые аналитические отчеты являются источником роста latency 
на hot path
### 2. Синхронные обращения к БД в hot path
Auction Engine во время аукциона выполняет синхронные запросы к БД для получения ставок и данных компаний. Из этого 
следует, что:
+ Отсутствует КЕШ для горячих данных, что является блокером для снижения нагрузки
+ Есть прямая зависимость времени ответа аукциона от нагруженности БД
+ Компонент уязвим в случае деградации БД

### 3. Отсутствие буферизации
Statistics Service в синхронном режиме пишет клики и показы на прямую в БД. Это означает, что:
+ есть прямая зависимость от количества запросов. При росте RPS количество insert/update операций растет 
пропорционально трафику
+ без асинхронного режима, у системы нет возможности сглаживать пики нагрузки
+ отсутствует изоляция streaming event от transactional потока, в том числе от критического RTB-потока 

Все это в совокупности создает высокую write-нагрузку и конкуренцию за ресурсы БД и повышает риск деградации БД.
  
### 4. Аналитика на продакше БД
Analytics Service выполняет тяжелые SQL-запросы по той же БД, что и обслуживает основные бизнес операции. Это влечет,
повышение риска деградации latency для остальных взаимодействий с БД.

## Точки отказа
|                Точка                | Последствие                                                                            |
|:-----------------------------------:|:---------------------------------------------------------------------------------------|
|   Single instance для PostgreSql    | Полная потеря работоспособности платформы                                              |
|           Auction Engine            | Проигрыш аукциона, причина - невозможность отвечать на bid request                     |
| Statistics Service с прямой записью | Отсутствие актуальных данных - потеря событий кликов и показов при перегрузке БД       |
|            Ручной deploy            | Длительный downtime и rollback, риск появления инцидентов из-за человеческого фактора  |
|      Отсутствие резервирования      | Утеря данных в том числе исходного кода                                                |
|       Отсутствие SRE практик        | Затруднение или невозможность своевременного обнаружения деградаций и выяснения причин |

## Архитектурные проблемы
1. Пересечение критичных и некритичных потоков в одном монолите и одной БД
2. Не возможность независимого масштабирования отдельных компонентов, в том числе latency критичных
3. Отсутствие репликации и кеширования
4. Отсутствие асинхронного взаимодействия для обработки событий
5. Отсутствие контейнеризации и ручной deploy

## Приоритетные направления для изменений
+ Перевод streaming event с синхронного режима в асинхронный через Kafka
+ Добавление БД Redis для кеширования данных: кампаний, ставок, таргетинга и быстрых бюджетных проверок
+ Создание репликаций БД: read реплики для аналитического кластера, write реплики для сбора статистики
+ Организация автоматизированного CI/CD процесса с автоматическим rollback
+ Выделить из монолита критический сервис Auction Engine

## Вывод
Текущее решение достигло своего предела. P95 latency не отвечает требованиям уже при текущей нагрузке и тем более
не ответит плановым параметрам. В дополнение отсутствует запас производительности для роста трафика. Как итог, система 
не готова к увеличению трафика, а значит не готова к интеграции с новой DSP, которая должна увеличить трафик на 20%.

Текущие проблемы нельзя решить вертикальным масштабированием по ряду причин: слишком много точек увеличения нагрузки 
на ключевые компоненты, бюджетные ограничения и использование не подходящих технологий для некоторые информационных потоков.
