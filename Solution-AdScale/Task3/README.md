# Task 3. Данные, масштабирование и отказоустойчивость
Директория: Solution-AdScale/Task3

## Цель
Разработка комплексной стратегии управления данными для микросервисной архитектуры AdScale, которая включает в себя:
* <b><i>Распределение данных:</i></b> закрепление конкретных баз данных за каждым сервисом в соответствии 
с его паттерном нагрузки
* <b><i>Масштабируемость:</i></b> определение методов горизонтального и вертикального роста хранилищ
* <b><i>Производительность:</i></b> внедрение многоуровневого кэширования для соблюдения жестких SLA по задержкам
* <b><i>Интеграцию:</i></b> построение асинхронного обмена данными через потоковую платформу
* <b><i>Надежность:</i></b> обеспечение целевых показателей RPO/RTO и механизмов восстановления после сбоев

## Состав артефактов

## Краткий обзор
В архитектуре реализован принцип Database per Service:
* <b><i>PostgreSQL</i></b> выступает транзакционным ядром для данных, требующих строгой консистентности (кампании, 
финансовые операции, бюджеты, конфигурация ставок)
* <b><i>ClickHouse</i></b> используется как аналитическое хранилище для потоковой обработки событий, статистики 
и построения витрин данных
* <b><i>Redis Cluster</i></b> обслуживает горячий путь (RTB hot path), обеспечивая доступ к данным с задержкой 
менее 1 мс и полностью исключая синхронные SQL-запросы в этом треке
* <b><i>Kafka</i></b> функционирует как единая шина событий (event backbone) с периодом хранения (retention) 
от 7 до 30 дней, обеспечивая асинхронную интеграцию и источник истины для проекций

Отказоустойчивость:
* <b><i>Financial Service:</i></b> применяется синхронная репликация, гарантирующая нулевую потерю данных (RPO = 0).
* <b><i>Statistics Service:</i></b> состояние восстанавливается путем переигровки событий из Kafka (replay), 
что исключает потерю данных в пределах окна ретенции.
