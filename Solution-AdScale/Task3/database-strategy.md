# Database per Service: распределение данных и выбор технологий

## Основной принцип
Каждый сервис владеет собственной изолированной базой данных. Прямой доступ к чужим БД запрещен — взаимодействие 
происходит исключительно через API сервиса-владельца. Это обеспечивает независимое масштабирование, изоляцию отказов 
и возможность выбора оптимальной СУБД под конкретный паттерн нагрузки. Legacy PostgreSQL сохраняется временно 
для функций монолита и выводится из эксплуатации по мере декомпозиции.

<b>Матрица выбора баз данных</b>

|       Сервис       |  Основная БД   | Дополнительная  БД |    Тип нагрузки    | Ключевое обоснование                                                                                                         |
|:------------------:|:--------------:|:------------------:|:------------------:|:-----------------------------------------------------------------------------------------------------------------------------|
|  Bidding Service   |   PostgreSQL   |       Redis        |     OLTP + Кэш     | Транзакционные обновления бизнес-правил в Postgres; микросекундный доступ к конфигурации в Redis для соблюдения P95 ≤ 100 мс |
|  Campaign Service  |   PostgreSQL   |         —          |        OLTP        | Сложные связи (кампания => таргетинг => креативы), транзакционность правок, развитые возможности SQL-фильтрации              |
|   Budget Service   |   PostgreSQL   |       Redis        |     OLTP + Кэш     | Строгая консистентность балансов (ACID, оптимистичные локи); Redis для атомарного `INCR` (frequency cap) и fallback-лимитов  |
| Statistics Service |   ClickHouse   |         —          | OLAP (Write-heavy) | Column-oriented хранение, быстрый bulk insert из Kafka, мгновенные агрегации (GROUP BY) по миллионам строк                   |
| Analytics Service  | ClickHouse/DWH |         —          | OLAP (Read-heavy)  | Тяжёлые отчёты рекламодателей, витрины данных (materialized views)                                                           |
| Financial Service  |   PostgreSQL   |         —          |   OLTP (Strict)    | ACID для балансов, идемпотентность операций, аудит-лог проводок, очереди через `FOR UPDATE / SKIP LOCKED`                    |

## Детализация архитектурных решений

### Bidding Service: PostgreSQL + Redis
* <b><i>PostgreSQL:</i></b> Хранит конфигурацию бизнес-правил. Объём данных мал, но критична целостность: 
некорректная ставка напрямую влияет на выручку. Требуются ACID-гарантии для обновлений.
* <b><i>Redis:</i></b> Обслуживает hot path. Синхронный SQL-запрос в RTB-треке недопустим по latency. Redis обеспечивает
P99 < 1 мс. Данные в Redis — это TTL-копия из BiddingDB.

### Campaign Service: PostgreSQL
* <b><i>Структура:</i></b> Нормализованная модель для хранения иерархии сущностей.
* <b><i>Шардирование:</i></b> По `campaign_id` (или `advertiser_id`) на уровне партиционирования таблиц. Детали 
масштабирования — в [`scaling.md`](scaling.md).

### Budget Service: PostgreSQL + Redis
* <b><i>PostgreSQL:</i></b> Хранит текущее состояние бюджета (одна строка на кампанию). Использует оптимистичные 
блокировки по полю `version` для предотвращения двойного резервирования.
* <b><i>Redis:</i></b> Выполняет две функции:
  1. Кэш доступного бюджета с TTL 5 секунд (fallback при недоступности Budget Service).
  2. Атомарный счётчик `freq:cap:{user_id}:{campaign_id}` через команду `INCR`.

### Statistics Service: ClickHouse
* <b><i>Паттерн:</i></b> Потребление событий из Kafka и их агрегация.
* <b><i>Почему не PostgreSQL:</i></b> При нагрузке в тысячи `INSERT` PostgreSQL конкурирует за WAL и упирается в I/O. 
Row-oriented хранение делает аналитические запросы (`COUNT`, `SUM`) медленными. ClickHouse с движком MergeTree 
оптимизирован для bulk insert и аналитических выборок.

### Analytics Service: ClickHouse → DWH
* <b><i>Этап 1 (Текущий):</i></b> Единый кластер ClickHouse. Разделение нагрузки через нейминг: база `stats_raw` 
для сервиса статистики и `analytics_views` для витрин.
* <b><i>Этап 2 (Целевой, через 12 мес):</i></b> При росте трафика до 50 000 RPS объём сырых событий превысит возможности 
одного кластера. Переход на выделенный DWH (ClickHouse Cloud, Apache Doris) с ETL-пайплайном (Airflow/Spark)
для разделения operational и analytical workloads.

### Financial Service: PostgreSQL
* <b><i>Требования:</i></b> Строгая транзакционность и аудит.
* <b><i>Идемпотентность:</i></b> Ключ идемпотентности и баланс обновляются в одной транзакции.
* <b><i>Очереди:</i></b> Для обработки финансовых задач используется паттерн `SELECT ... FOR UPDATE SKIP LOCKED`.
* <b><i>Отказ от NoSQL:</i></b> Eventual consistency недопустима для денежных балансов, а горизонтальное масштабирование
write-нагрузки не требуется.
* <b><i>Outbox Pattern:</i></b> Для обеспечения долговечной фиксации расчетного факта и повторяемой доставки 
используется таблица `outbox`. Факт списания фиксируется в транзакции с балансом и публикуется в Kafka
через Outbox Relay Worker.

## Изоляция данных в период миграции
В течение первых 3 месяцев применяется паттерн Strangler Fig:
* Новые сервисы (Bidding, Campaign, Budget, Financial) разворачиваются с собственными инстансами PostgreSQL.
* Legacy PostgreSQL обслуживает только оставшиеся функции монолита.
* ClickHouse разворачивается как абсолютно новый кластер, не создающий нагрузки на легаси-базу.
* Поэтапный вывод данных из Legacy PostgreSQL происходит без остановки бизнес-процессов.
