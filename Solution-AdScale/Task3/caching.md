# Кэширование
##
## Какие данные кэшируются
Кэширование в системе разделено на три уровня: данные hot path аукциона, служебные структуры (сессии, лимиты) и 
строгие исключения для финансовых операций.

### Hot path аукциона (Hot Path)

Данные, необходимые для принятия решения за миллисекунды. Читаются Bidding Service и Ad Server.

|               Ключ                |       Тип        | Что хранит                                                        |     Кто читает     |      TTL       | Инвалидация                         |
|:---------------------------------:|:----------------:|:------------------------------------------------------------------|:------------------:|:--------------:|:------------------------------------|
|     `campaign:{campaign_id}`      |       Hash       | Флаг активности, потолок ставки, профиль таргетинга, ID креативов | Bidding, Ad Server |      60 с      | CDC из Campaign DB                  |
|      `budget:{campaign_id}`       |   String/Hash    | Остаток, дневной лимит, состояние pacing                          |      Bidding       |      5 с       | CDC + события `impression` из Kafka |
| `targeting:segment:{segment_id}`  |       Set        | Множество `user_id` в сегменте                                    |      Bidding       |       —        | Batch-job из Analytics              |                          
| `freqcap:{user_id}:{campaign_id}` | String (counter) | Счётчик показов в текущем окне                                    |      Bidding       | 3600 с (1 час) | TTL + события `impression` из Kafka |
|     `creative:{creative_id}`      |       Hash       | Разметка, URL, размеры креатива                                   |  Delivery Service  | 300 с (5 мин)  | CDC из Campaign DB                  |

<b>Особенности реализации:<b>
* <b><i>Бюджет (TTL 5 с):</i></b> Короткий TTL минимизирует риск перерасхода при использовании fallback. Устаревший
лимит на 5 секунд допустим.
* <b><i>Конфигурация (TTL 60 с):</i></b> Рекламодатели меняют настройки редко. Более короткий TTL создал бы избыточную
нагрузку на Campaign Service при cache miss.
* <b><i>Атомарность:</i></b> Счётчик `freqcap` использует атомарную команду `INCR`, что исключает race condition
при параллельных запросах.
* <b><i>Активные кампании:</i></b> Для быстрой фильтрации используется множество `campaign:active:set` (или флаг 
`active` внутри хэша кампании).

### Сессии, дедупликация и Rate Limiting
|           Ключ           |       Тип        | Назначение                                     |          TTL          |
|:------------------------:|:----------------:|:-----------------------------------------------|:---------------------:|
|  `session:{token_hash}`  |       Hash       | Сессии пользователей личного кабинета          |      Сессионный       |
| `ratelimit:dsp:{dsp_id}` |    Sorted Set    | Rate limiting запросов от DSP (timestamps)     |    Скользящее окно    |
|   `ratelimit:ip:{ip}`    | String (counter) | Rate limiting по IP-адресу                     |    Скользящее окно    |
|    `dedup:{event_id}`    |      String      | Флаг обработки события для Idempotent Consumer | \>= окна replay Kafka |

## Что НЕ кэшируется
* <b><i>Финансовые балансы:</i></b> Источник правды — Finance PostgreSQL primary. Использование stale-данных в денежных 
операциях недопустимо.
* <b><i>Bid responses:</i></b> Каждый запрос уникален (зависит от пользователя, контекста страницы и текущего времени),
кэшировать ответы бессмысленно.
* <b><i>Бинарные файлы креативов:</i></b> Хранятся в Object Storage. В Redis находятся только метаданные и URL.
* <b><i>Сырые события (impression/click):</i></b> Транслируются в Kafka, не в кэш.

## Инвалидация кэша (Cache Invalidation)

Используется гибридный подход, сочетающий три стратегии для баланса между актуальностью данных и нагрузкой на систему.

|     Стратегия      | Применение                                     | Механизм                                                                                                                          |
|:------------------:|:-----------------------------------------------|:----------------------------------------------------------------------------------------------------------------------------------|
| Event-driven (CDC) | Кампании, бюджеты, креативы (критичные данные) | При изменении в CampaignDB Debezium публикует событие в Kafka. Consumer (Bidding/Ad Server) удаляет (DEL) ключ в Redis            |
|       По TTL       | Frequency capping, сегменты таргетинга, сессии | Данные считаются валидными в течение окна TTL. Инвалидация происходит автоматически по истечении срока                            |
|     По версии      | Creative-метаданные, большие targeting-индексы | Ключ содержит версию: `campaign:{id}:v{version}`. При обновлении publisher инкрементит версию, новые запросы идут по новому ключу |

## Прогрев кэша (Cache Warming)

Для предотвращения лавины cache miss и перегрузки БД при старте используется поэтапный прогрев.

<b>Сценарии запуска:</b>
* <b><i>Старт сервиса:</i></b> initContainer в Kubernetes. Под не получает трафик (Readiness Probe = false), пока 
прогрев не завершён.
* <b><i>Rolling update:</i></b> Новый под прогревает кэш, пока старый ещё обслуживает трафик (overlapping readiness).
* <b><i>Новый Redis-шард:</i></b> One-shot job для заполнения шарда.
* <b><i>Перед ожидаемым пиком:</i></b> Ручной запуск перед массовыми событиями.

<b>Алгоритм прогрева Campaign Service:</b>
1. Запрос из CampaignDB всех активных кампаний (`status = ACTIVE`).
2. Сортировка по приоритету (Top-N по `bid_price DESC`).
3. Запись в Redis батчами по 500 ключей через `PIPELINE`.
4. Установка флага `ready=true`.

<b>Безопасность прогрева:</b>
* Пагинированное чтение из БД с rate-limit.
* Использование `PIPELINE` для минимизации round-trips.
* Readiness Probe учитывает не только готовность процесса, но и достижение целевого `cache_hit_ratio` на тестовом 
трафике.
