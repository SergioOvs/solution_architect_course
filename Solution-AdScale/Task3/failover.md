# Отказоустойчивость данных и соответствие стандартам 12-факторного приложения
## Цели восстановления (RPO и RTO)
|         Сервис          |  RPO (Потеря данных)  | RTO (Время простоя) | Обоснование                                                                    |
|:-----------------------:|:---------------------:|:-------------------:|:-------------------------------------------------------------------------------|
|    Financial Service    | 0 (отсутствие потерь) |        3 мин        | Синхронная репликация; полная сохранность транзакций обязательна               |
|     Budget Service      |       30 секунд       |      90 секунд      | Риск расхождений в балансах при потере данных о резервировании                 |
|    Campaign Service     |       10 минут        |       8 минут       | Кампании критичны для бизнеса, но кратковременная потеря данных допустима      |
|     Bidding Service     |       45 минут        |       5 минут       | Правила аукциона меняются редко; восстановление из резервной копии             |
| ClickHouse (Statistics) |         1 час         |      20 минут       | Возможность полного восстановления через переигровку событий из Kafka (7 дней) |
| ClickHouse (Analytics)  |        3 часа         |        1 час        | Агрегированные витрины данных могут быть перестроены из сырых логов            |
|          Kafka          | 0 (гарантия доставки) |       8 минут       | Отказоустойчивость за счет репликации (factor = 3); данные хранятся 7 дней     |
|          Redis          |  Не применимо (N/A)   |      3 минуты       | Временное хранилище; актуальное состояние подтягивается из основных БД         |

## Стратегия резервного копирования
<b>PostgreSQL (Bidding, Campaign, Budget, Financial)</b>
* <b><i>Физический бэкап (Base Backup):</i></b> Ежедневно в 01:00 UTC через `pg_basebackup`. Хранение: 5 ежедневных + 2 
еженедельных копии в S3 (отдельный регион).
* <b><i>Point-in-Time Recovery (PITR):</i></b> Непрерывное архивирование WAL в S3. Позволяет восстановить БД на любой 
момент за последние 7 дней. Критично для Financial Service при ошибках в транзакциях.
* <b><i>Валидация:</i></b> Автоматическое восстановление в изолированной среде раз в неделю с фиксацией времени 
в мониторинге.

<b>ClickHouse (Statistics, Analytics)</b>
* <b><i>Бэкап:</i></b> Инкрементальный clickhouse-backup по партициям (ежедневно, хранение 14 дней в S3).
* <b><i>Альтернатива:</i></b> Для Statistics Service приоритетен Kafka Replay (retention 7 дней). Восстановление 
из Kafka быстрее и дешевле, чем из бэкапа, если потеря данных укладывается в окно ретенции.

<b>Kafka</b>
* <b><i>Защита:</i></b> Replication factor = 3.
* <b><i>Архив:</i></b> Для долгосрочного хранения (1 год) финансовых событий используется Kafka Connect (S3 Sink Connector) или MirrorMaker.

<b>Redis</b>
* <b><i>Восстановление:</i></b> Полный сброс кэша с последующим прогревом (Cache Warming) из PostgreSQL. Время — ~2 минуты.
* <b><i>RDB snapshots:</i></b> Раз в 5 минут для ускорения перезапуска подов (не для disaster recovery).

## Восстановление после сбоя до публикации (Outbox Pattern)
Для обеспечения долговечной фиксации расчетного факта и повторяемой доставки используется паттерн Outbox в Finance Service.

<b>Сценарий сбоя:</b>
Транзакция в `FinanceDB` закоммичена, запись в таблице `outbox` имеет статус `PENDING`, но Kafka недоступна 
или вернула ошибку.

<b>Алгоритм восстановления (Outbox Relay Worker):</b>
1. Worker с периодичностью (1 секунда) делает выборку: 
`SELECT * FROM outbox WHERE status = 'PENDING' FOR UPDATE SKIP LOCKED LIMIT 100;`
2. Для каждой записи worker пытается опубликовать событие в Kafka топик `financial.events` с использованием
`transactional.id`.
   1. <b><i>При успехе:</i></b> Обновляет статус записи в `outbox` на `SENT` (или удаляет запись) в той же транзакции, 
   что и коммит Kafka.
   2. <b><i>При ошибке:</i></b> Транзакция публикации откатывается. Запись в `outbox` остается в статусе `PENDING`.
   Worker повторит попытку на следующем цикле.
   3. <b><i>Dead Letter Policy:</i></b> Если публикация не удается N раз (например, 50 попыток), статус меняется 
   на `FAILED`, а событие копируется в топик `financial.events.dlq` для ручного разбора.

## Соответствие принципам 12-факторного приложения
|       Фактор        | Реализация в AdScale                                                                   |
|:-------------------:|:---------------------------------------------------------------------------------------|
|      Codebase       | Один репозиторий на сервис (или монорепо с четкими границами)                          |
|    Dependencies     | Явное объявление зависимостей (`go.mod`, `requirements.txt`)                           |
|       Config        | Все настройки (DSN, URL Kafka, API-ключи) — через переменные окружения или K8s Secrets |
|  Backing Services   | PostgreSQL, Redis, Kafka — внешние ресурсы, подключаемые по URL из окружения           |
| Build, Release, Run | CI/CD: Build (Docker) => Release (Тег + Конфиг) => Run (Deployment)                    |
|      Processes      | Stateless-сервисы. Состояние только в БД/Кэше/Очередях                                 |
|    Port Binding     | Сервис сам слушает порт (gRPC :50051, HTTP :8080)                                      |
|     Concurrency     | Горизонтальное масштабирование подов (K8s HPA) по RPS                                  |
|    Disposability    | Быстрый старт (< 10 сек), graceful shutdown (30 сек) с коммитом Kafka offset           |
|   Dev/Prod Parity   | Идентичные Docker-образы и версии БД/Кафка в локальном `docker-compose`                |
|        Logs         | Structured logging (JSON) в stdout/stderr. Агрегация через Fluentd/Loki                |
|   Admin Processes   | Миграции БД (Flyway/Liquibase) — отдельные K8s Job перед деплоем                       |

## Health чеки, как дополнительная мера отказоустойчивости
<b>Liveness (`/healthz`):</b> Проверка, что процесс жив. При провале — перезапуск пода.
<b>Readiness (`/readyz`):</b> Проверка доступности БД, Redis и прогрева кэша. При провале — исключение 
из Service Load Balancer.
